## 2. 개선 전략 (7가지)

**전략 1. 개요를 그림과 표로 다시 연다** (원칙 4, 피드백 1.1)
- 맨 위에 시연 영상 / 대표 GIF. 군중전 → 보스 등장 → 3인칭 보스전을 그림 3칸 표로 나란히 보여 줍니다(원칙 17).
- 소개 한 문단 + 맡은 일 두 줄 + 목표. `《》` 라벨과 "이 문서는 두 파트로…" 문단은 지웁니다.
- 목표에 **개발 목표 ③**을 더합니다: "두 번째 보스를 다른 사람이 같은 틀 위에서 만들 수 있게 한다"(결정 ④에 있는 이유). 회고에서 8.5로 받아 줍니다.
- 개요 끝에 SHIFTER식 표 "핵심 / 부딪힌 문제 / 이렇게 풀었다"를 둬, 문서가 깊게 다루는 것을 한눈에 보여 줍니다.

**전략 2. Part 구분을 제목 단계로 바꾼다** (피드백 3)
- `# Part 1. 팀 리딩` → `## 2. …` → `### 2.1 …` → `#### 2.1.1 …`
- 상세 문서의 목차는 `##`·`###`만 보여 주므로, Part 줄은 목차에 안 나오고 장·절만 나옵니다. 넣은 뒤 `doc.html`과 빌드(슬라이드)에서 Part 제목이 문서 제목으로 잘못 읽히지 않는지 확인이 필요합니다.

**전략 3. 결정은 "질문형 절 제목 + 표 1 + 문단 1"** (원칙 11·13)
- `결정 ①~⑤` 번호와 `[결정과 이유]` 같은 라벨을 없애고, 절 제목 자체를 질문으로 씁니다(Super Phage "3.3 이동 로직을 공유할 것인가"처럼).
- 결정 ①은 표가 두 개(취합 분류, 카드 매핑)인데, 카드 매핑 표는 3~4줄만 남깁니다.
- 결정 ⑤ 제목: "원거리 전격 포를 공기 흡입으로 바꾼 이유" → "기획한 패턴을 바꿀 것인가"

**전략 4. 모든 절을 그림으로 연다** (원칙 7·20)
- 이미지 자리를 절 맨 앞으로 옮기고, 캡션은 그림 바로 아래 기울임 한 줄.
- 7장은 `boss_components.png`를 장 첫머리로 올리고, 구조 그림 바로 아래에 클래스 역할 표를 붙입니다(피드백 7.1). "나란히 보기"는 상세 문서 렌더러가 지원하지 않아, 같은 화면에 이어 보이게 하는 것까지만 합니다.

**전략 5. 코드는 장마다 1~2블록, 15줄 안팎** (원칙 21)
- Part 2 코드 12 → 7 안팎. 남길 후보:

| 절              | 남길 코드                         | 빼는 코드                                       |
| --------------- | --------------------------------- | ----------------------------------------------- |
| 8.3.1 패턴 선정 | 후보 고르기 `foreach`             | `GetWeight` (문장 한 줄로)                      |
| 8.3.2 생명주기  | `TryBeginAttack` · `EndAttack`    | `Update` 뼈대 (거의 주석뿐 → 흐름 그림으로)     |
| 8.4.1 등장 낙하 | `Land`                            | `OnWindup` (단계 표에 이미 있음)                |
| 8.4.2 짓밟기    | (없음 — 8.3.1에서 설명)           | `MeetsStartCondition`                           |
| 8.4.3 마그마    | `BuildVolleyPlan` (15줄로 줄여)   | `OnActiveTick`, 초기 속도 식, `HasCover` → 문장 |

- 4.2 씬 YAML은 짧게 남기거나(6줄) 그림으로 바꿉니다.

**전략 6. 표 칸은 짧게, "~다"나 명사로** (원칙 14·15·16)
- 음슴체 칸을 모두 고칩니다. 긴 칸은 표 아래 bullet으로 내립니다.
- 9.4 마그마 단계 표처럼 수치가 많은 표는 수치를 그 절의 본문으로 옮기고 표에는 의미만 남깁니다.

**전략 7. 회고는 목표 → 결정 묶음 → 아쉬움 → 배운 점** (원칙 4·6)
- 10.1: 개요의 목표 ①②③을 "구현해 볼 수 있었다"로 받아 주는 표.
- 10.2: 결정들을 하나의 질문으로 묶는 표. 후보 질문: **"정해 둔 것보다 의도를 기준으로 판단했는가"** — 결정 ②(피드백 기준), ⑤(기획 패턴 변경), ④(공통 틀), ③(이벤트 기준)이 모두 같은 질문에 답합니다.
- 배운 점은 앞 장을 다시 말하지 않고, 결정 묶음 표에서 나온 한두 가지만.

## 4. 작업 순서 (안)

## 5. 정해 주셔야 할 것

1. **결정 번호(①~⑤)를 없앨지.** 원칙대로면 없애고 절 제목을 질문으로 씁니다. 다만 결정 ⑤처럼 다른 장에서 "결정 ⑤"로 부르던 곳은 "§8.1.2"로 바뀝니다.
2. **2.2 감정 단계 이름.** 피드백은 "주도권 회복", "보스와 대치"가 감정이 맞냐는 것입니다. 지금 이름은 상황에 가깝습니다. 기획서(`_intake/참고 자료/HivePurge 컨셉 기획서.md` 38·50~54줄)를 확인해 보니, 지금 문서의 이름은 기획서 그대로이고 **기획서 안에서도 흐름 문장과 표의 이름이 다릅니다**(흐름 "보스의 갑작스러운 등장 → 패턴을 읽고 극복함" ↔ 표 "보스와 대치 → 성취"). 그래서 문서만 고칠지, "기획서는 이렇게 썼다"를 살리고 문서에서만 감정 이름으로 정리할지 정해야 합니다. 감정 이름으로 바꾸는 예: 압도감 → 해방감 → 긴장 → 위압감 → 성취감. **이건 제 예시일 뿐**이라, 실제로 의도한 감정을 말씀해 주시면 그걸로 씁니다.
3. **2.3 간트 차트로 바꾸면 표는 지울지.** 원칙 19(같은 것 두 번 안 넣기)대로면 지웁니다. 보내 주신 간트 코드는 돌진형 합류와 후반 압박이 둘 다 2:00부터 90초로 겹쳐 있는데, 원래 표도 "2:00 이후"와 "2:00~3:30"이라 의도대로인지 확인이 필요합니다.
4. **개발 목표 ③을 개요에 넣을지.** 결정 ④의 "두 번째 보스는 다른 사람이 만든다"를 처음부터 목표로 두셨던 것이면 넣고, 하다 보니 그렇게 된 것이면 넣지 않습니다.
5. **회고 10.2의 묶는 질문.** 후보: "정해 둔 것보다 의도를 기준으로 판단했는가". 다른 질문이 더 맞으면 바꿉니다.
