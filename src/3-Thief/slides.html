VehicleSession.cs
private void HandleVehicleInput(string userId, string json)
{
    VehicleInputMessage message =
        JsonSerializer.Deserialize<VehicleInputMessage>(json);

    // (Why) 보낸 사람은 서버가 아는 접속 ID로 채운다
    message.UserId = userId;
    message.Steer = Math.Clamp(message.Steer, -1f, 1f);
    message.Accel = Math.Clamp(message.Accel, 0f, 1f);
    message.Brake = Math.Clamp(message.Brake, 0f, 1f);
    message.Gear  = Math.Clamp(message.Gear, 0, 2);

    _ = broadcastAsync(message);
}

증상

튜토리얼에서 본 게임으로 넘어가면, 비호스트 화면의 차가 시작 위치가 아닌 곳에 놓였습니다.

원인

호스트가 전환 직전에 보낸 상태가 늦게 도착해, 새 씬에서 튜토리얼의 차 위치가 적용됐습니다. 메시지만 보고는 어느 씬의 상태인지 알 수 없었습니다.

씬마다 번호(씬 버전)를 매겼습니다. 번호가 다른 상태는 서버와 클라이언트 양쪽에서 버리고, 비호스트는 새 씬에서 차를 시작 위치로 옮깁니다.

증상

로비에서 게임 씬으로 넘어가면 서버 연결이 끊겼습니다.

원인

다른 스크립트가 Awake보다 먼저 Instance를 읽으면 instance가 미리 채워집니다. 예전 Awake는 instance가 비어 있을 때만 DontDestroyOnLoad를 불러서 이 경우 건너뛰었고, 연결을 든 오브젝트가 씬과 함께 파괴됐습니다.

해결

다른 인스턴스면 파괴하고, 아니면 항상 자신을 등록하고 DontDestroyOnLoad를 부르도록 순서를 바꿨습니다.

SingletonBase.cs — 바꾼 뒤의 Awake
protected virtual void Awake()
{
    T self = this as T;

    if (instance != null && instance != self)
    {
        Destroy(gameObject);
        return;
    }

    instance = self;

    // (Why) Instance가 Awake보다 먼저 찾았더라도
    //       반드시 씬 전환 대상에서 뺀다
    DontDestroyOnLoad(gameObject);
}

입력은 보낸 사람별로 키를 나눴습니다(vehicle_input:u2) — 액셀과 브레이크가 같은 칸을 덮어쓰면 한 사람의 입력이 사라지므로.

첫 버전

방 전체에 보낼 때 Task.WhenAll로 모두 끝날 때까지 기다렸습니다. 느린 한 명의 송신 동안 그 브로드캐스트를 부른 수신 루프·틱까지 함께 멈췄습니다.

  • 1접속자마다 송신 루프 — 보내는 쪽은 큐에 넣고 신호만 준 뒤 바로 돌아온다
  • 2신호는 OutboundSignalPending으로 한 번만 — 메시지가 100개 와도 루프는 100번 깨지 않는다
  • 3이벤트가 64개 넘게 밀리거나 3초 안에 못 보내면 그 접속자만 끊는다

while (member.Socket.State == WebSocketState.Open)
{
    await member.OutboundSignal.WaitAsync(token);

    lock (member.OutboundGate)
        member.OutboundSignalPending = false;

    // 이벤트는 반드시 먼저, 순서대로 전송한다
    while (member.Events.Reader
               .TryRead(out string eventJson))
        await SendRawAsync(member, eventJson, token);

    // 상태는 각 종류별 마지막 값만 전송한다

            await SendRawAsync(member, stateJson, token);
    }
}

private async Task TryStartPendingMiniGameAsync()
{
    if (currentMiniGameType != null) return;

    string[] memberIds = getMemberIds();

    // (Why) 한 명이라도 준비 전이면 시작하지 않는다
    foreach (string memberId in memberIds)
        if (readyUsers.Contains(memberId) == false) return;

    string operatorId =
        memberIds[Random.Shared.Next(memberIds.Length)];
    currentMiniGameType = pendingMiniGameType;
    pendingMiniGameType = null;

    await broadcastAsync(new MinigameStartedMessage
    {
        MiniGameType = currentMiniGameType,
        OperatorId = operatorId
    });
}

private async Task HandleFuelPressAsync(string userId)
{
    await gate.WaitAsync();

    try
    {
        // … 지금 주유 미니게임인지·준비 단계인지 확인

        if (fuelOperatorId != userId)
            return;

        fuelPhase = FuelPhase.Fueling;
        fuelPressedAt = DateTime.UtcNow;

        await broadcastAsync(new FuelStateMessage
            { GaugePercent = 0f, IsPressed = true });
    }
    finally
    {
        gate.Release();
    }
}

네 명이 각자 맡은 조작을 지연 없이 한 대의 차에 모아 함께 운전할 수 있게 되었습니다.

01
미니게임 3종을 한 클래스에 모았다

3종으로 정해져 있어 MiniGameSession 하나로 괜찮다고 봤지만, 단계와 판정이 붙으며 635줄까지 커져 Room의 문제를 한 단계 아래로 옮긴 셈이 되었습니다. 나눌 필요를 느꼈지만 당장 동작에 문제가 없었고, 일정 부담이 커서 리팩토링하지 못했습니다.

배운 점

나누는 기준은 "몇 개 만들까"가 아니라 "한 클래스가 맡는 일이 얼마나 늘어나나". 같은 틀이 반복되는 기능은 처음부터 하나씩 클래스로.

02
입력 지연을 빌드에서야 발견했다

입력 지연 누적은 에디터에서는 드러나지 않고 빌드에서만 나타났습니다. 에디터와 빌드는 vSync 설정부터 달랐고, 그래서 통합 테스트 기간이 지나서야 원인을 찾기 시작했습니다.

배운 점

에디터에서 잘 돌아가는 것과 실제 환경에서 잘 돌아가는 것은 다르다. 네트워크 기능은 붙일 때마다 빌드로 함께 테스트해야 한다.
